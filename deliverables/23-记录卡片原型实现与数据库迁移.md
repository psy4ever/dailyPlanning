# 记录卡片原型实现与数据库迁移

日期：2026-10-22。Android / API 配套版本：0.3.0。

本轮以用户附图为当前记录模块的依据，替代文档 22 中“入口列表、模块各自选日”的结构。实现的是应用内的服务卡片样式。

## 页面与交互

| 原型区域 | 当前实现 |
|---|---|
| 记录首页 | 直接显示今日热量环、摄入、运动消耗、三大营养素进度、收入和支出；保留睡眠入口 |
| 日期 | 首页与详情共享选日；支持前后一天、日历选日和回到今天 |
| 饮食详情 | 紧凑热量环、按餐次列出食物、克数与热量，底部固定“记录饮食” |
| 添加饮食 | 早餐 / 午餐 / 晚餐 / 加餐切换，食物搜索，选择食物并调整克数，可多项保存 |
| 食用量 | 克数输入、加减、按食物营养快照计算热量与三大营养素；保存食用量后回到所选列表，整餐保存后落库 |
| 收支详情 | 收入与支出合计、笔数、全部 / 收入 / 支出筛选、分类与备注列表 |
| 记一笔 | 支出 12 类 / 收入 4 类网格、金额、备注、当天时间；支持新增、编辑、删除 |
| 返回 | 详情隐藏主导航；页面返回与 Android 返回均可使用 |

原型样例数字没有写入正式数据库。热量预算和营养目标由用户在“饮食记录 → 预算与运动”填写；未设置显示 `—`。目前为当天目标，运动消耗手工输入，尚未接入健康平台或自动推荐算法。食物图库沿用手工营养库，列表配以食物表情图标；没有生成示例食物数据。

依原型的 `1570 − 419 = 1151`，还可吃 = 当天热量预算 − 已知摄入，运动消耗独立显示；超过预算时显示“已超出”。营养缺失时标明待补全数量。

## 数据库判断

不需要推翻原数据库。`food_versions`、`intakes` 和 `intake_items` 已能支撑食物选择、多餐、多食物及营养快照；账目类型、金额和时间也已存在。采用 Room v10 → v11 增量迁移：

| 表 | 补充内容 |
|---|---|
| `ledger_entries` | 可空 `category` 分类键、`note` 备注；保留原 `source`，不猜测旧账目的分类 |
| `nutrition_days` | 新增当天目标表：`id`、`date`、`timezone`、`budgetKcal`、`exerciseKcal`、`proteinGoal`、`fatGoal`、`carbGoal`、`version` |

日期与时区有唯一索引，ID 由日期与时区确定，避免设备间同日目标生成两个记录。目标和金额按十进制字符串保存；编辑使用版本检查。业务表共 18 张、129 个字段；云同步辅助表仍独立管理。未使用清库或破坏性重建。

JSON 整库备份升级为 v11，可恢复 v8/v9/v10/v11；旧账目自动补空分类与备注，旧备份没有目标表时恢复为空表。原有绑定云账户后禁止整库覆盖的规则继续生效。

## 云端配套

同步契约升级为 v2，两端的 `sync-contract.json` 保持一致；新增 `nutritionDay` 聚合、账目分类与备注，变更纳入离线队列与冲突处理。服务端仍通过现有 MySQL JSON 聚合表持久化，无需删除或重建生产库。

历史云端账目读取时补充空字段；旧版已排队账目请求仍可幂等重试。客户端同步前检查契约，遇到旧服务端时保留本机记录并提示配套升级。

本地部署包在 `dist/cloud-release`，镜像标记 `daily-rhythm-api:0.3.0`。需要按文档 18 上传该包并运行升级，随后安装新 APK。当前没有部署用户云服务器，没有执行生产 SQL。

## 验证

- Android Debug / 测试 APK 构建、单元测试与 Lint；营养计算覆盖克数换算、未知营养、未知份量。
- 隔离设备数据库验证 v10 → v11 保留旧账目、目标版本冲突、v10 旧备份恢复及 v11 新备份往返。
- Compose 页面验证首页卡片跳转、收入 / 支出保存后合计刷新、日期切换、食物选择、40 克面包换算为 205 千卡，以及保存整餐后的剩余热量刷新。
- 原有本地持久化 / 事务测试、专用 H2 回环服务器的真实 HTTP 三模块同步；新增营养目标、账目分类与备注的往返核验。
- 服务端 H2 集成测试覆盖新字段、营养目标合法性、旧账目重试和读取兼容；未将测试指向生产 MySQL。

最终结果：14 项模拟器测试、4 项 Android 单元测试、19 项服务端测试全部通过；Debug APK 构建与 Lint 无错误，部署包 SHA-256 清单 12/12 匹配。
