# 日有度｜产品需求与首版设计 v0.2

日期：2026-10-19 · 优先平台：Android · 状态：需求与设计稿，尚非可安装 App。

## 1. 产品决定

**定位：一个帮助用户提前安排、轻量记录、理解个人回报并调整生活节奏的私人时间账本。**

核心闭环：计划 → 开始/结束/补记 → 对比计划和实际 → 按自己的价值权重复盘 → 调整下一天。

用户已确认 Android 优先；后端按 Java + Spring、数据库 MySQL 规划。网络条件尚未进一步确认，本方案以“无公网也能完成核心使用”为基线：手机本地保存，电脑上的服务是可选扩展。手机完全离线和局域网联调的区别见技术方案。

重要修订：回报不能只代表工资。收入、社交、娱乐、成长、健康等维度由用户选择、命名并设置权重；**配置是启用回报分析的必填步骤**。基础记录可以先使用，不用为了开始记一笔而被长问卷拦住。无权重配置时不生成综合分。

### 1.1 优先解决的事

- 计划太满、遇到变化后放弃：提供缓冲、缩小任务和改期，保留原计划用于对比。
- 忘记记录、记录太累：一键开始/结束、常用模板、事后补记，不要求全天逐分钟填写。
- 只看到打卡，没看到真实行为：计划与实际独立存储，打卡不自动产生虚构时长。
- 不清楚投入是否值得：把时间、金钱、精力和个人价值分开观察。
- 作息饮食散落：睡眠、三餐和加餐与行为放在同一个日历语境，但避免重复计时。
- 想记录热量却缺少可信数据：先让用户维护食物的每 100g 营养数据与每次实际食用量，明确未知项；常用食物可以复用。

### 1.2 不在首版范围

社交社区、排行榜、强制锁机、监控其他 App、医疗诊断、自动减重处方、全自动排程、付款订阅、多设备实时协作、复杂向量数据库。饮水和生理周期仅预留模块与入口，正式记录能力不列为首版核心。AI 和联网均不应成为记录的前提。

## 2. 品牌与页面

**appName：日有度**。工作英文标识：DailyPlanning。标语：把每一天，过得有据可循。

名称是设计候选，未完成商标和各应用商店重名核验；上架前再确认。

**appIcon：开放的时钟圆环 + 勾形指针 + 琥珀色圆点。** 圆环代表时间，勾代表行动，缺口代表允许留白。独立 PNG 见 `design/app-icon-v1.png`；它是视觉源稿，上架前仍需制作 Android adaptive foreground/background、单色层及目标商店要求的尺寸。

### 2.2 信息架构

底部三项：**今天 / 记录 / 我的**。“洞察”暂不完成，也不在当前导航展示；早期概念图中的洞察画面只作历史视觉参考。

| 页面 | 从上到下的版式 | 主要操作与状态 |
|---|---|---|
| 今天 | 日期与周条 → 空日引导或今日时间线 → 其他活动 | 首项创建后隐藏空日焦点卡；左侧节点串联时间线；卡片点主体看计划与执行详情，卡片快捷完成；添加后续计划用“+ 计划” |
| 记录 | 顶部日期 → 已知摄入 → 饮食 → 睡眠 → 记账本 | 日期只在页顶切换；各弹窗只选时刻；账本记录收入/支出、来源、金额 |
| 我的 | 本机档案 → 备份与恢复 | 昵称可选；明确目前没有登录和同步；旧权重、时间类别、项目数据暂时保留但设置入口移除 |
| 计划编辑 | 标题 → 开始/结束时分下拉框 → 固定/灵活 → 提醒 | 使用当前选中日，不重复选择日期；结束在同日且晚于开始 |
| 批量复用 | 选择来源日计划 → 日期范围 → 星期 → 跳过已有日期 → 确认 | 日期仅属于复用目标选择；每个目标日生成独立计划，不复制执行记录 |
| 行为结束 | 实际时间 → 分类 → 关联计划 → 可选感受 → 稍后评价 | 停止计时后先可靠落盘，评分可留到晚间集中完成 |
| 晚间回顾 | 计划/实际差异 → 未评价活动 → 今日一个感受 → 明日一个调整 | 不强迫补齐一整天；允许“今天先到这里” |
| 食物数据维护 | 搜索已有食物 → 新建/编辑食物 → 输入每 100g kcal 与可选三大营养素、数据来源、生熟状态 | 用户数据优先；单位与来源明确；旧餐食保持录入当时的营养快照 |
| 添加一次摄入 | 选择早餐/午餐/晚餐/加餐 → 时间 → 添加多个食物 → 各自食用量 → 保存 | 加餐可无限次独立记录，不强行并入邻近正餐；未知份量允许暂存但不贡献“已知热量” |
| 记录模块管理 | 核心模块固定显示；可选模块清单 → 开启/关闭 → 模块专属入口 | 关闭仅隐藏入口和提醒，不删除数据；饮水/生理周期为后续模块，敏感内容有独立隐私设置 |

首版视觉中的日期、时长、餐食、热量和分数全部是显式标注的演示，不是用户真实记录。静态概念图用于视觉方向，需求和算法以本文及技术文档为准。图中的热量数值不构成摄入建议；未确认个人目标时不画“目标进度”。

### 2.3 饮食记录的最短流程与扩展

用户从“记录”选择餐次或加餐 → 选食物/创建自定义食物 → 输入份量（首版以克为标准）→ 查看每项与本餐的已知热量 → 保存。下一次可复用食物与份量；营养数据提供包装标识手填、用户手填和将来获授权资料导入三种来源，首版不依赖联网食品库。用户所说的“营养价目表”在本方案解释为**营养成分表**；若还希望记录食品价格，可给食物增加可选单价字段，但价格不参与热量计算。

### 每日计划作为可复用文档

手动创建、前一天复用、文件导入与未来 AI 排程使用同一个版本化 `DailyPlanDocument` 草稿。文档的 `date` 是来源日元数据，每项只有当天开始分钟与时长，必须在当天结束；新建/调整表单直接使用页顶选中的日期。导入先预览，确认后为目标日生成新 ID。批量复用可选连续日期范围及星期，默认跳过已有计划的日期；每个目标日独立保存，不复制完成状态或执行记录。运行中的计划仍保存在规范化 Room 表中，以便改期历史、活动关联、提醒和备份保持单一可信来源。

记录页面只在顶部切换日期。饮食和账本的弹窗只选该日时刻；睡眠按醒来日归属，入睡时刻晚于醒来时刻时按前一晚记录。账本记录收入/支出、来源和正金额，暂不推断币种或自动与活动现金字段合并。当前为本机单用户：首次进入“我的”建立稳定本机 ID，可设置昵称；账号认证、多设备同步、数据拥有权迁移待后续设计。原“数据管理”明确更名为“备份与恢复”：导出 JSON，恢复会替换本机记录。

早餐/午餐/晚餐是便于选择的分类；**加餐可在任意时间添加多条**。例如 10:30 咖啡、16:00 酸奶都单独计入当日。水、无糖饮料等需要能在模块设置中决定是否作为“饮水记录”出现；含能量饮料要进入食物摄入明细，避免只记水量而漏记能量。

今日热量标题为“已知摄入”，并标出待补全项数量。没有确认营养值或份量的项目不强行填 0；存在未知项时不能称为“今日总摄入”。UI 不默认设置 1,800 kcal 等通用目标。后续如需要用户目标，单独定义来源、适用范围、修改记录及“不设目标”选项。

扩展记录模块遵循相同入口、导航与样式，但各自拥有独立数据与权限：睡眠、饮食为首版记录域；饮水、生理周期、情绪、运动等是可选域。生理周期数据默认为私密，不自动发送到 AI 或服务端。用户自定义记录可先支持“名称 + 数值/文本/时间 + 单位 + 日期”的轻量模板；临床意义、公式和跨模块推断不由用户模板自动产生。

## 3. 回报模型：历史方案，当前暂停

本节保留早期研究，当前导航、我的权重设置与活动评价入口已移除；以下规则不构成本轮交付或当前页面要求。

### 3.1 必填配置

首次进入个人回报分析时，选择或创建一个评价模型。至少一个启用维度；每个维度名称非空且模型内不重复，权重为正数。需要权重为零时使用“停用”，不要暗中计入。建议最多 6 个常用维度以减少填写成本，允许高级设置扩展。

| 预设示例 | 权重 | 归一化比例 |
|---|---|---|
| 均衡体验 | 社交 3、娱乐 3、收入 3 | 33.3%、33.3%、33.3% |
| 收入优先 | 收入 4、社交 2、娱乐 2 | 50%、25%、25% |
| 自定义 | 用户自己添加名称和权重 | 系统按总和计算，不要求凑成 10 或 100 |

预设只是填写辅助，用户必须点“确认我的权重”，不能未经确认套用默认值。收入也不是必选维度。

每个维度可填写“对我意味着什么”和评分锚点。例如社交的 8 分可能代表有深度的交流，而不是认识人数；娱乐的高分可以代表充分放松。收入维度默认也是“对收入目标的贡献”的用户自评，不把工资绝对值直接转成分数。

### 3.2 三类信息分开

1. **偏好权重**：我重视什么，相对稳定、可以调整。
2. **实际获得**：一次活动在各维度的 0–10 分自评，允许暂不填。0 是“确认没有获得”，空值是“不知道/未评价”。
3. **付出事实**：时长、直接支出、可选精力消耗 1–5；现金收入单列，不自动代表所有价值。

活动可以是工作、学习、与朋友吃饭、游戏、运动或休息。系统不预设娱乐低于工作，也不把休息判断为低价值。

工作可同时带来收入、成长和社交；聚餐也可能带来娱乐与社交。维度是价值标签，时间主分类仍只有一个，避免一小时被算成三小时。

### 3.3 结果展示

显示“个人回报 76.7/100（主观自评）”、各维度得分/权重/贡献、已评价覆盖率，并把“用时 90 分钟、支出 ¥20、精力消耗 2/5”放在旁边。**不命名为科学幸福分，不跨用户排名。**

同一组评分：社交 8、娱乐 6、收入 9。3:3:3 时总分 76.7；4:2:2 且收入权重为 4 时总分 80.0。改变权重会改变结果，因此历史记录必须保留模型版本。

工作净时薪、含通勤时薪仅在用户记录金额后显示，作为现金维度的补充，不主导个人回报。

## 5. 关键状态与异常

- 计划：草稿 → 已安排 → 已完成/部分完成/改期/取消。计时中的状态属于行为会话，不能与计划状态混为一张枚举。
- 会话：运行 → 暂停 → 运行 → 结束；每次运行生成独立片段，片段相加得到实际时长。
- 新手：先安排一件事；回报页明确“设置你的价值权重后开始分析”，不显示零分。
- 已漏记：显示“有 4 小时未记录”，提供补记；不能直接推断在玩手机。
- 重复提交：相同操作 ID 只生效一次；双击结束不会增加时长。
- 日期切换：今日未结束只统计到当前时刻，未来时间为“尚未发生”，不是未记录。
- 多活动同时发生：例如吃饭听课，选主活动计入时间，听课保留次标签；用户可重新分配。
- 权重修改：生成新版本；旧报告保留旧权重，支持显式切换到当前模型重算。
- AI 不可用：继续记录与本地统计；页面显示“建议暂不可用”，不伪造分析。
- 数据迁移失败：保留旧数据库和备份，不清库重建。
- 饮食数据不全：某次加餐缺份量时，已知 kcal 只累加完整条目；统计同时显示“1 项待补全”，不得把已知合计误称为全天总热量。
- 食物数据更新：自建食物从 100 调整为 120 kcal/100g 后，已保存餐食保留当时版本和快照；新记录使用新版。
- 可选模块关闭：停止展示与提醒，但不隐式删除饮水/周期记录；用户可从数据管理单独导出或删除。

## 6. 自用完成度与阶段计划

### 自用可发布到自己手机的门槛

完成 R01–R15 及 R20 的最小形式；可不做云账号、社交、AI、自动识餐和可选健康模块。饮食至少能维护手工营养成分表并计算三餐与加餐的已知热量。复杂重复计划可以先用复制昨天替代。

上线自己的使用习惯前验收：

- 连续两周真机试用；飞行模式、锁屏、进程被杀、手机重启后，已保存数据不丢。
- 有意义的测试：跨日切片、重叠不重复、计时暂停恢复、权重归一化、缺失评分、模型版本、三餐加餐热量、未知项、食物版本、备份恢复。
- 高频行为控制在 1–2 次主要操作；目标为每日额外记录时间中位数不超过 3 分钟。这是待验证的产品目标，不是已达成性能。
- 用户能只记三件重点事，也能看到有效反馈，不要求 24 小时全覆盖。
- 若权重填写造成负担：维度配置仍必填，但活动打分留到晚上批量完成，不阻塞结束计时。

### 单人开发建议顺序

| 阶段 | 交付 | 粗估工作量* |
|---|---|---|
| A | Android 工程、Room、计划、计时、补记 | 6–10 人日 |
| B | 睡眠、食物表、三餐加餐、热量统计、权重配置、活动评分 | 8–14 人日 |
| C | 备份恢复、提醒、真机边界验证 | 4–7 人日 |
| D | Spring + MySQL、本地连接与同步 | 5–10 人日，可后置 |
| E | 规则建议 → AI/API → RAG | 验证需要后单独估算 |

*用于范围讨论，不是交付承诺；取决于 Android 熟悉程度。每天兼职两小时不能按一个人日计算。先完成 A–C 并实际使用，再扩展 D/E。
