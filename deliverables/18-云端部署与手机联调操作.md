# 云端部署与手机联调操作

日期：2026-10-21；2026-10-22 更新。目标服务器 Ubuntu 24.04.4，公网 IP `43.142.121.249`；MySQL 8.4.11 已在服务器验收。三模块代码和本地集成验收见[文档 17](17-三模块云同步实现映射与验收.md)。用户最后确认服务器运行 `0.2.1`；本机最新待部署包为 `0.2.4`，包含自动发放数字 UID、昵称/密码登录。服务器仍需上传、启动和验收。

用户尚未确认域名。本阶段使用 SSH 加密隧道，后端只绑定服务器 127.0.0.1:18080，MySQL 不发布端口；无需新增付费服务。正式 HTTPS 在第 6 节配置。

## 1. 本机生成部署包

【本机 PowerShell】，构建脚本先执行后端测试和打包；测试默认使用独立 H2。已有专用 MySQL 测试库的验证记录见文档 17。

```powershell
cd C:\code\dailyPlanning
powershell -ExecutionPolicy Bypass -File .\deploy\build-bundle.ps1
```

输出目录 `C:\code\dailyPlanning\dist\cloud-release`，包含生产 JAR、固定 Java 21 镜像的 Dockerfile、独立健康检查类、Compose 扩展、凭据准备和启动脚本、备份恢复及定时器；`SHA256SUMS` 记录文件摘要。不包含 `.env`、密码、测试资源或生活数据。

Android APK：`C:\code\dailyPlanning\android\app\build\outputs\apk\debug\app-debug.apk`。重新生成命令：

```powershell
cd C:\code\dailyPlanning\android
.\gradlew.bat :app:assembleDebug :app:assembleDebugAndroidTest :app:lintDebug --console=plain
```

## 2. 上传并启动后端

【本机 PowerShell】：

```powershell
scp -r "C:\code\dailyPlanning\dist\cloud-release" ubuntu@43.142.121.249:~/
```

【已登录的云服务器 SSH 终端】：

```bash
cp -R ~/cloud-release/. ~/daily-rhythm/
cd ~/daily-rhythm
bash start-api.sh
```

脚本会：

1. 核对部署文件摘要。
2. 首次部署才询问初始昵称和 App 密码（8–16 个 ASCII 字符，不含空白、引号、`$`、`#`、反斜杠）；密码输入不回显，保存到已有 `.env`，保留 MySQL 原密码。已设置的旧登录名（本例 `yuan`）留作过渡期别名，不需重设密码；数字 UID 由服务器发放，不在此输入。不要把凭据发到聊天。
3. 对现有数据库创建加密逻辑备份，然后仅清理之前验收用的 `_deploy_verify_20261021` 表。
4. 必要时从当前 Ubuntu 包仓库安装 `docker-buildx`，构建 API 镜像。
5. 启动后端，Flyway 建立业务存储表，等待 MySQL 与 API 健康，检查 `/health`。

**预期：** API 和 db 都是 healthy，最后返回 `{"status":"ok"}`。脚本可以重复执行，保留已有登录凭据。修改 `.env` 中的 App 密码不会自动更改已有账户密码。

### 已完成的 UID 迁移背景

先前镜像 `daily-rhythm-api:0.2.1` 已通过 Flyway V2 把原唯一登录名变为 UID，并补充可重复的昵称。当前 `yuan` 可继续作为 UID，密码、内部账户 ID、云端记录及同步游标不变；旧 APK 的登录请求在过渡期仍可用。更新包时先在【本机 PowerShell】上传，再到【云服务器 SSH 终端】重跑启动脚本：

```powershell
cd C:\code\dailyPlanning
scp -r .\dist\cloud-release ubuntu@43.142.121.249:~/
```

```bash
cp -R ~/cloud-release/. ~/daily-rhythm/
cd ~/daily-rhythm
bash start-api.sh
```

脚本先备份现有数据库，再构建新镜像、迁移 V2 并等待健康检查。**不要删除 `.env`、MySQL 容器卷或卸载主设备 App。** 成功后用 `adb install -r` 安装新版 APK，保留本机记录。SSH 隧道可继续使用。

### 更新自动发放 UID 与统一个人资料卡（0.2.3）

用户上次反馈运行 `0.2.1`；本轮 `0.2.3` 加入由数据库发号的注册接口。Flyway V3 为现有账户分配八位数字 UID，并把旧登录名留作别名；若正式库目前只有 `yuan` 一户，它获得 `00000001`。原密码哈希、owner ID 及业务数据不变。先按第 1 节重新生成部署包，再按本节上方命令上传并在服务器运行 `bash start-api.sh`。脚本在迁移前创建加密备份；看到 api/db 均 healthy 后，在本机用 `adb install -r` 安装新 Debug APK。**仅更新 APK 不会让旧服务器拥有数字 UID 注册接口。** 无需重新输入已保存的初始账户密码，也不需新建数据库。

若提示找不到 openssl，在服务器安装 `sudo apt-get install -y openssl` 后重试。若拉取 Java 镜像超时，保留报错，按已有腾讯云内网镜像配置检查；不切换到未知公共镜像。首次迁移若发现其他未知表，会报错停止，不开启自动 baseline 或清空数据库。

### 当前待部署版本（0.2.4）

按第 1 节重新生成部署包，再在**本机 PowerShell**上传、**服务器 SSH 终端**运行第 2 节命令。`0.2.4` 使用昵称和密码登录，也保留 UID 与旧 `yuan` 登录名；昵称重复时先按密码区分，同名且密码也相同时需用唯一 UID。Flyway V3 自动迁移既有账户，V4 为昵称查询建立非唯一索引；密码哈希、owner ID 和业务数据不变。**只更新 APK、未更新服务器时，新的昵称登录与注册不能保证成功。**

排错输出（不要直接分享展开后的 `docker compose config` 或 `.env`）：

```bash
sudo docker compose -f compose.yaml -f compose.api.yaml ps -a
sudo docker compose -f compose.yaml -f compose.api.yaml logs --tail 60 api
```

## 3. 通过 SSH 隧道联调

另开【本机 PowerShell】，执行后保持该窗口开启。连接成功时不持续输出文字是正常的：

```powershell
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:18080:127.0.0.1:18080 ubuntu@43.142.121.249
```

再开一个【本机 PowerShell】验证：

```powershell
curl.exe --fail http://127.0.0.1:18080/health
```

预期 `{"status":"ok"}`。如果端口占用，先确认并停止之前的本地测试服务器或隧道，不终止不明进程。

若 App 创建账户一直等待，先在**电脑 PowerShell**重试上面的 `curl.exe`。如果提示无法连接 `127.0.0.1:18080`，表示本机 SSH 隧道没有运行；保持运行 `ssh -N ...` 的窗口开启，再重新提交注册。若健康检查正常但昵称登录失败，按第 2 节更新 API 至 `0.2.4`。模拟器控制台里的 GLES、SnapshotInfo、puid 警告不能单独说明注册失败；以 `/health` 和 App 提示为准。

更新 Debug APK 时使用 Android Studio 运行，或先 `adb devices` 确认设备后执行 `adb -s <设备序列号> install -r <APK完整路径>`。`-r` 保留已有应用数据，不卸载主设备验证恢复。

在 App“我的 → 账户与同步”可选择“登录”或“创建账户”；已有 `yuan` 账户时可暂用 `yuan` 和原密码登录，页面随后展示分配的数字 UID。创建账户只填写昵称和 8–16 位密码；创建成功即登录，之后优先用昵称/密码登录。UID 仅用于同名同密码时区分账户，也请保存。**不填写 UID 或服务器网址来注册。** 开发版自动选择连接地址：

- Android Studio 模拟器：内部使用 `http://10.0.2.2:18080`。
- USB 连接真机：先在本机执行 `adb -s <设备序列号> reverse tcp:18080 tcp:18080`，内部使用 `http://127.0.0.1:18080`。
- 登录时使用昵称和 App 密码，和 MySQL 用户密码分开。资料卡仍显示 UID；编辑昵称会更新本机与云端，UID 不变。一个本机安装只能绑定一个云账户，已有绑定时不能直接注册另一个新账户。

如需保留一份独立副本，先在“我的 → 数据迁移”导出本机记录。登录后自动合并同步三个模块；有冲突时在账户入口处理。Debug 的 HTTP 例外仅限这些本机地址；从本机到云服务器的流量走 SSH 隧道。正式日常使用配置 HTTPS。发给朋友的 APK 没有电脑隧道，不能直接连接当前云端。

## 4. 三模块云端联合验收

在测试设备执行并记录：

| 模块 | 测试操作 |
|---|---|
| 计划 | 新建、改期、复制/批量生成、完成或取消；关联活动开始/暂停/继续/结束，核对历史与片段 |
| 记账 | 新建收入和支出、修改金额、删除；重复点同步不重复建账 |
| 饮食 | 创建食物、记录三餐/加餐、修改食物营养版本；确认历史摄入快照不变，验证摄入修改/删除/恢复 |

然后断网新增三个模块记录，恢复网络后点“立即同步”，应清空待同步数量。存在冲突时预览本机和云端内容后处理；食物历史冲突保留云端后再新增营养版本。

【云服务器 SSH 终端】只查询记录组数量：

```bash
cd ~/daily-rhythm
sudo docker compose exec -T db sh -c 'MYSQL_PWD="$MYSQL_PASSWORD" mysql --protocol=TCP -h127.0.0.1 -u "$MYSQL_USER" "$MYSQL_DATABASE" --execute="SELECT kind,COUNT(*) AS records_count FROM cloud_records GROUP BY kind;"'
```

应至少看到 `plan`、`ledger`、`food`、`intake`；计时、分类或项目有记录后出现对应 kind。明细与修订保存在记录组 payload 中，不单独计为 root 行。

使用另一份干净测试安装登录，拉取后核对三个模块与历史快照。使用独立测试设备，保留主设备现有安装。重启云端 db 与 api 后再次检查健康及读取：

```bash
sudo docker compose -f compose.yaml -f compose.api.yaml restart db api
sudo docker compose -f compose.yaml -f compose.api.yaml up -d --wait --wait-timeout 240 api
```

完成这些实际云端操作后再将联合验收标记通过；本地测试不替代本节。

## 5. 备份、独立副本和恢复

在三个模块写入测试数据后，【云服务器 SSH 终端】：

```bash
cd ~/daily-rhythm
python3 backup.py
```

备份流程是 MySQL 一致性逻辑导出、gzip、OpenSSL AES-256-CBC/PBKDF2 加密及 HMAC-SHA256 验证；保留最近 7 个完整备份。输出 `.enc` 和 `.enc.hmac`，密钥在 `~/daily-rhythm/.backup-key`，权限 600。恢复前先验证 HMAC，失败时不解密或写库。

用刚输出的备份文件路径执行（替换文件名）：

```bash
python3 restore-check.py backups/<刚生成的文件名>.enc
```

脚本创建带随机名称的内部 Docker 网络、临时 MySQL 和 API 容器；恢复到独立数据目录，逐个验证所有记录组的字段、关联及业务规则，再测试认证和业务接口读取，最后只移除本次创建的临时容器和卷。正式数据库不作为恢复目标。

预期最终 `Isolated restore, aggregate relationships, authentication and API read passed.`。本脚本需要当前 App 密码与备份中的账户密码一致；密码轮换后恢复旧备份时，应使用对应凭据在隔离环境验证。

【本机 PowerShell】保存服务器之外的备份副本及单独密钥：

```powershell
scp -r ubuntu@43.142.121.249:~/daily-rhythm/backups "$env:USERPROFILE\daily-rhythm-backups"
scp ubuntu@43.142.121.249:~/daily-rhythm/.backup-key "$env:USERPROFILE\.daily-rhythm-backup-key"
```

密钥单独保管，不与加密文件一起公开或写进 Git；丢失密钥无法解密。定时器只产生服务器内备份，独立副本仍需定期拉取并核对。

手动备份与恢复均通过后，启用每日北京时间 03:15 附近的备份任务。先确认 ubuntu 用户可非交互执行 Docker，再安装定时器：

```bash
sudo -n docker info --format '{{.ServerVersion}}'
sudo install -m 644 daily-rhythm-backup.service daily-rhythm-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now daily-rhythm-backup.timer
sudo systemctl start daily-rhythm-backup.service
sudo systemctl status daily-rhythm-backup.service --no-pager
sudo systemctl list-timers daily-rhythm-backup.timer --no-pager
```

若第一条要求密码或失败，先处理定时任务的 Docker 执行权限，不盲目启用。失败记录查看 `sudo journalctl -u daily-rhythm-backup.service --since today --no-pager`；外部通知尚未配置。

## 6. 正式 HTTPS

确认可用域名后，将 API 子域名 A 记录解析到服务器公网 IP，按现有部署路线核对正式服务条件，然后在服务器 `.env` 增加 `API_DOMAIN=实际域名`。不要填写示例域名或 IP 代替真实配置。

在腾讯云防火墙和主机入口允许 80/443，保持 MySQL 不发布端口。执行：

```bash
cd ~/daily-rhythm
sudo docker compose -f compose.yaml -f compose.api.yaml -f compose.https.yaml config --quiet
sudo docker compose -f compose.yaml -f compose.api.yaml -f compose.https.yaml up -d gateway
sudo docker compose -f compose.yaml -f compose.api.yaml -f compose.https.yaml logs --tail 40 gateway
```

Caddy 根据域名申请和续期证书，证书保存在独立卷；域名解析和 80/443 可达要求见 [Caddy 官方说明](https://caddyserver.com/docs/automatic-https)。从手机正常验证 HTTPS 后，用 `-PcloudApiBaseUrl=https://实际域名` 构建正式 APK；地址由应用配置，登录界面仍只输入 UID 和密码。同一个账户 ID 会继续使用原同步历史；不跳过证书校验。

## 更新和回滚

每次部署前生成一致性备份，并保存当前已验证的 JAR/镜像。首版 Flyway V1 为新增业务存储表，应用回滚应保留这些表和持久卷；后续迁移须按版本评估兼容性。可以停止 API 并恢复上一份已验证镜像，数据库恢复先在隔离环境演练，不直接用旧备份覆盖正式库。不要运行 `docker compose down -v`。
