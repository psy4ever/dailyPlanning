# 日有度｜HTTP API 与字段契约 v0.2（设计稿）

日期：2026-10-19。用于将来 Spring 服务端与 Android 本地 Repository 对齐；**尚无已实现接口或真实返回**。字段名、枚举、格式是本轮提案，启动编码前应确认并固定为 OpenAPI 文件。文中的数值示例均非用户数据。

## 1. 通用约定

| 项 | 规则 |
|---|---|
| 根路径 | `/api/v1`；JSON，UTF-8。资源名复数、小写、连字符。 |
| 身份 | 服务端由会话/令牌确定用户；请求体不接收 `ownerId` 作为权限依据。纯离线版用本地 profile。 |
| ID | UUID 字符串，由客户端在离线创建时生成，服务端校验格式并防重复。 |
| 时刻 | ISO 8601 UTC，例如 `2026-10-19T08:10:00Z`；涉及“某日”均另传 IANA `timezone`，例如 `Asia/Shanghai`。 |
| 金额和营养数值 | JSON 十进制字符串，例如 `"1180.0"`，避免 Java/JS 二进制浮点误差；整数秒/毫升用 JSON integer。 |
| 写入幂等 | 创建或状态切换带 `operationId`（UUID）；相同 ID/请求只应用一次。更新带 `expectedVersion`，版本不符返回 409。 |
| 通用响应 | 单体 `{data:{...},schemaVersion:1}`；列表 `{data:{items:[...],nextCursor:null|"..."},schemaVersion:1}`。`id,version,createdAt,updatedAt` 为保存后的字段。 |
| 空值 | `null` 表示未获知/未填；数值 `0` 表示确认的零。UI 不得把 null 当 0。 |
| 分页 | `limit` 1–100，默认 30；`cursor` 为不透明字符串。小型日摘要可不分页，明细列表可分页。 |
| 错误 | 400 请求格式，401 未认证，403 无权限，404 不存在，409 版本/时段冲突，422 字段无效；体 `{error:{code,message,fieldErrors:[{field,reason}],requestId}}`。 |

字段样例 `UUID`、状态码、限值等都是设计约定，非现成服务端事实。对于开发者而言，当前所有路径的实现状态为 `TODO`。

## 2. 食物营养表（nutrition 模块，P0）

食物含稳定的 `foodId`，营养数据有递增 `version`。用户维护的“价目表”按**每 100g 营养成分表**理解；若需要价格，单独存 `priceAmount,priceCurrency,priceBasisGrams`（P1），不与 kcal 计算混合。

### `POST /foods`、`POST /foods/{foodId}/versions`

新建食物/发布新营养版本。修改名称或营养值均新建版本；老版本只读。停用用 `PATCH /foods/{foodId}` 的 `archived`，不删除旧餐食引用。

| 请求字段 | 类型/约束 | 含义 |
|---|---|---|
| `operationId` | UUID，必填 | 幂等写入 |
| `name` | string 1–120，必填 | 食物名称；例“无糖酸奶” |
| `brand` | string 或 null | 包装品牌；非包装食物可空 |
| `preparedState` | `RAW`,`COOKED`,`PACKAGED`,`UNKNOWN`，必填 | 生/熟/包装状态；不得把生重数据直接套熟重 |
| `kcalPer100g` | decimal string ≥0，必填 | 每 100g 可食部的 kcal；用户明确录入或包装换算 |
| `proteinGPer100g`,`fatGPer100g`,`carbGPer100g` | decimal string ≥0 或 null | 三大营养素克数，未提供保持 null |
| `sourceType` | `USER_LABEL`,`USER_ESTIMATE`,`IMPORTED`，必填 | 营养数据来源；导入功能到 P1/P2 才启用 `IMPORTED` |
| `sourceNote` | string ≤300 或 null | 包装/来源说明，不编造权威出处 |
| `expectedVersion` | integer，改版必填 | 基于哪一版修改 |

返回 `foodId,version,name,brand,preparedState,kcalPer100g,proteinGPer100g,fatGPer100g,carbGPer100g,sourceType,sourceNote,archived,createdAt,updatedAt`。食物能量已知而蛋白质未知是合法状态；不要用 4/4/9 自动覆盖包装的 kcal。

### `GET /foods?q=&cursor=&limit=`、`GET /foods/{foodId}?version=`

搜索结果按用户常用/名称排序，由服务端返回 `items[]`，各项包括 `foodId,latestVersion,name,brand,preparedState,kcalPer100g,sourceType,archived`。仅在打开食物选择器时搜索；查询为空时返回最近/常用，是否有默认推荐库待确认。取指定版本时返回全部营养字段，旧版本可读。

## 3. 一次摄入与加餐（nutrition 模块，P0）

### `POST /intakes`、`PATCH /intakes/{intakeId}`

`intake_event` 代表一次进食；一次可有多个食物。早餐/午餐/晚餐/加餐都可同日多次，`mealType` 只作分类，不是唯一键，也不由时钟自动推断。`PATCH` 用完整 `items[]` 替换本次摄入的明细，防止增量操作顺序不清；返回新版本。

| 请求字段 | 类型/约束 | 含义 |
|---|---|---|
| `operationId` | UUID，必填 | 幂等键 |
| `expectedVersion` | integer，PATCH 必填 | 乐观锁 |
| `eatenAt` | UTC datetime，必填 | 实际摄入时间 |
| `timezone` | IANA string，必填 | 记录时区，决定本地统计日 |
| `mealType` | `BREAKFAST`,`LUNCH`,`DINNER`,`SNACK`，必填 | 加餐可有多次 |
| `note` | string ≤500 或 null | 可选说明 |
| `items` | array 1–30，必填 | 本次摄入的食物列表 |
| `items[].itemId` | UUID，PATCH 时可提供 | 稳定条目 ID；新条目由客户端生成或留空后服务端生成，具体策略待编码确认 |
| `items[].foodId` | UUID 或 null | 引用自建/导入食物；空则需要 `manualName` |
| `items[].foodVersion` | integer 或 null | 选中食物时必须带所见版本；服务器不能静默换成新版 |
| `items[].manualName` | string 或 null | 未知营养食物的临时名称 |
| `items[].consumedGrams` | decimal string >0 或 null | 可食部实际克数；未知时保持 null |

服务端根据 `foodId+foodVersion` 取营养数据，并在响应保存快照。客户端提交的热量展示值**不作为可信计算输入**；离线同步时可提交已签名的本地快照版本供冲突处理，规则需另行细化。

| 响应字段 | 类型 | 含义 |
|---|---|---|
| `intakeId,version,eatenAt,timezone,mealType,note` | 见请求 | 保存后的摄入对象 |
| `items[].itemId,foodId,foodVersion,displayName,consumedGrams` | UUID/int/string/decimal/null | 保存的每项 |
| `items[].kcalPer100gSnapshot` | decimal string 或 null | 该次计算使用的营养快照 |
| `items[].calculatedKcal` | decimal string 或 null | 有 kcal 与克数才计算；未知返回 null |
| `items[].nutritionStatus` | `COMPLETE`,`MISSING_FOOD`,`MISSING_AMOUNT` | 明确缺失类型 |
| `knownKcal` | decimal string | 本次完整项目合计；可为 `"0"`，但有缺项时只是部分已知值 |
| `incompleteItemCount` | integer | 缺营养或缺份量的项目数 |

例：16:10 的一条 `SNACK` 可含酸奶和香蕉；11:00 又可有另一条 `SNACK`。`GET /intakes?date=2026-10-19&timezone=Asia/Shanghai&cursor=&limit=30` 返回上述结构的 `items[]`。删除 `DELETE /intakes/{id}` 使用 `expectedVersion` 与 `operationId`，服务端软删除并保留恢复/同步标记。

### `GET /nutrition/daily?date=&timezone=`

| 响应字段 | 类型 | 含义 |
|---|---|---|
| `date,timezone` | date/string | 查询口径 |
| `knownKcal` | decimal string | 当天完整摄入项的合计 |
| `incompleteItemCount` | integer | 有记录但缺营养或份量的食物项数；没记晚餐不算一项缺失 |
| `isComplete` | boolean | 仅表示“当前已记录的条目都能计算”；不保证真实全天饮食完整 |
| `mealBreakdown[]` | array | 每项 `mealType,knownKcal,eventCount,incompleteItemCount` |
| `updatedAt` | datetime | 读模型更新时间，便于缓存判定 |

示例早餐 310 + 午餐 520 + 加餐 350 = **已知 1,180 kcal**。晚餐还未记录时 `incompleteItemCount=0`，仍只称“已知摄入”，不能声称全天完整；若午餐另有一项缺克数，则 `incompleteItemCount=1`。目标热量字段不进入首版摘要，未来由用户自设目标模块提供。

## 4. 计划、行为和作息（核心 P0）

| 接口 | 关键请求字段 | 关键返回字段与刷新时机 |
|---|---|---|
| `GET /plans?date=&timezone=` | 本地日期/时区 | `items[].id,title,scheduledStart,scheduledEnd,priority,fixed,status,baselineVersion,version`；进今天/切日期取 |
| `POST /plans`、`PATCH /plans/{id}` | `operationId,title,scheduledStart,scheduledEnd,timezone,categoryId,priority,fixed`；PATCH 加 `expectedVersion,changeReason` | 保存的 `id,status,version`；只刷新当前日期的计划与时间线 |
| `GET /activities?from=&to=&timezone=` | 半开区间 UTC + 时区 | `items[].id,title,categoryId,planId,sessionStatus,segments[].startAt/endAt,version`；进今天取 |
| `POST /activities/{id}/start|pause|resume|finish` | `operationId,occurredAt,expectedVersion` | `id,sessionStatus,segments,version`；更新正在展示的活动；服务端校验状态转移 |
| `POST /activities/manual` | `operationId,title,categoryId,planId,startAt,endAt,timezone` | `id,segments,conflicts[],version`；时间重叠 409 并说明冲突对象 |
| `GET /sleep-logs?date=&timezone=` | 按醒来日 | `items[].id,onsetAt,wakeAt,awakeSeconds,quality,version`；进入记录且睡眠启用时取 |
| `POST /sleep-logs`、`PATCH /sleep-logs/{id}` | `operationId,onsetAt,wakeAt,awakeSeconds?,quality?`；PATCH 加 `expectedVersion` | 保存后的睡眠对象；失效同日记录摘要与时间构成 |

状态定义：计划 `DRAFT/SCHEDULED/COMPLETE/PARTIAL/RESCHEDULED/CANCELLED`；活动 `IDLE/RUNNING/PAUSED/FINISHED`。这些是提案枚举，编码前应对每一种状态转移建表确认。`scheduledEnd > scheduledStart`、`wakeAt > onsetAt`；暂停片段不计入时长。`priority` 取 1–3 的规则尚需产品确认，不在 UI 中伪造解释。

## 5. 回报与洞察（核心 P0）

| 接口 | 请求字段 | 响应字段 |
|---|---|---|
| `POST /value-models/{modelId}/versions` | `operationId,expectedVersion,confirmedAt,dimensions:[{dimensionId?,name,definition?,weight,scaleAnchors?}]`；至少一个维度，权重均 >0，名称不重复 | `modelId,version,confirmedAt,normalizedWeights:[{dimensionId,name,weight,share}]` |
| `PUT /activities/{id}/evaluation` | `operationId,expectedVersion,modelId,modelVersion,ratings:[{dimensionId,score0to10|null,note?}]` | `activityId,modelVersion,ratings,ratingCoverage,status,score|null,version` |
| `GET /analytics/time?from=&to=&timezone=` | UTC 半开区间与时区 | `from,to,timezone,windowSeconds,segments:[{categoryId,name,seconds,share}],unknownSeconds,coverage,dataRevision,algorithmVersion` |
| `GET /analytics/value?from=&to=&modelVersion=` | 日期窗与模型版本 | `score|null,status(COMPLETE/INCOMPLETE/NO_DATA),ratingCoverage,weights[],contributions[],ratedDurationSeconds,totalRecordedSeconds,algorithmVersion` |

时间构成 UI 只绘制**一条横向堆叠条**并逐行标时长与占比，包含未记录；它的 `segments[]` 保证和 `unknownSeconds` 合计等于 `windowSeconds`。今天只统计当前已发生时间，未来不计“未记录”。回报缺一项评分时 `score=null,status=INCOMPLETE`；不能在前端用已知分数重新归一化伪造最终分。

页面进入洞察后才加载默认可见时间窗；切到个人回报区、确认权重或改变模型版本时才加载对应价值报告。相同 `dataRevision+algorithmVersion+modelVersion+window` 的结果可复用；写入活动或评价使相关缓存失效。

## 6. 可选记录模块的预留契约（P1/P2，不阻塞核心）

| 接口 | 请求字段 | 响应字段/权限 |
|---|---|---|
| `GET /record-modules` | 无 | `items:[{key,displayName,enabled,privacyLevel,capabilities,version}]`；只返回入口元信息 |
| `PATCH /record-modules/{key}` | `enabled,expectedVersion` | `key,enabled,version`；关模块不删数据 |
| `POST/GET /hydration-entries` | POST `operationId,occurredAt,volumeMl>0,beverageType,linkedIntakeId?`；GET `date,timezone` | `id,occurredAt,volumeMl,beverageType,linkedIntakeId,version`；含热量饮料可关联摄入避免重计 |
| `POST/GET /cycle-entries` | POST `operationId,localDate,eventKind,flowLevel?,privateNote?`；GET `from,to` | `id,localDate,eventKind,flowLevel,version`；须独立私密授权，默认不供 AI 使用 |
| `POST/GET /custom-record-templates` | `name,fields:[{fieldKey,type,unit?,required,privacyLevel}]` | `templateId,version,fields`；模板更新产生版本 |
| `POST/GET /custom-records` | `templateId,templateVersion,occurredAt,values` | `id,templateVersion,values,version`；按模板版本校验，不对任意值做医学/营养推断 |

可选模块即使在代码结构上存在，也不意味着首版可用；UI 对未实现模块显示“规划中”，不提供无效输入按钮。生理周期具体事件枚举、提醒策略、隐私锁与本地加密方案均为 `TODO/待确认`，不能按猜测定稿。

## 7. 写入后的数据变化与避免重复请求

| 操作 | 源数据变化 | 需要更新 | 可复用/按需加载 |
|---|---|---|---|
| 保存食物新版本 | `food_definition` 版本增加 | 当前食物详情/搜索项 | 既有摄入保留旧快照，无需刷新旧日期营养报告 |
| 保存一次加餐 | `intake_event/items` 增加 | 当前日期摄入列表、营养摘要；可见的当天洞察营养区 | 权重报告、其他日期、睡眠与时间条不刷新 |
| 更新/删除摄入 | 指定 intake 版本变更 | 受影响日期的摄入与营养摘要 | 不预取整月食物数据 |
| 开启饮水模块 | 模块设置变更 | 其他记录入口 | 饮水明细等用户进入时再取 |
| 完成行为计时 | activity segments 变更 | 当前时间线和时间洞察；如正在看回报，失效回报缓存 | 饮食列表与食物表不刷新 |
| 修改回报权重 | 新模型版本 | 可见回报报告 | 时间构成、营养摘要和历史原版本报告可复用 |

本表是请求时机与刷新范围的依据。实际实现后要核对缓存失效；“少请求”不能导致过期数据。
