# 本地 Room / SQLite 数据库

验证日期：2026-10-21。当前使用 Room 2.8.5 管理 Android 自带 SQLite，安装并首次打开 App 后自动建库，数据保存在运行 App 的手机或模拟器里。

## 当前配置

| 配置 | 值 |
|---|---|
| App 包名 | `com.dayoudu.app` |
| 数据库文件 | `daily-rhythm.db` |
| 数据库版本 | 11 |
| 设备内路径 | `/data/user/0/com.dayoudu.app/databases/daily-rhythm.db` |
| 数据库入口 | `app/src/main/java/com/dayoudu/app/data/NutritionDatabase.kt` |
| Schema | `app/schemas/com.dayoudu.app.data.NutritionDatabase/11.json` |
| 验证设备 | `Medium_Phone_API_37.0`，API 37 模拟器 |

运行本地版无需配置数据库账号、密码或服务端连接地址。建库和 v1→v11 的升级注册由 Room 代码管理，不手工执行建表 SQL。2026-10-22 记录卡片改版增量添加账目分类、备注及当日营养目标表，详见[记录卡片迁移说明](../deliverables/23-记录卡片原型实现与数据库迁移.md)。下方原 v10 检查记录保留为历史验证快照。

18 张业务表包括：

- 计划：`plans`、`plan_revisions`。
- 当日营养目标：`nutrition_days`（v11 新增）。
- 活动：`activities`、`activity_segments`、`activity_tags`。
- 饮食：`food_versions`、`intakes`、`intake_items`。
- 睡眠：`sleep_logs`。
- 分类与项目：`time_categories`、`projects`。
- 本机档案与账本：`local_users`、`ledger_entries`。
- 旧回报模型及评分：`value_model_versions`、`value_dimensions`、`activity_evaluations`、`dimension_ratings`；现有 UI 暂停该入口。

## 在 Android Studio 中查看

1. 打开本目录，启动模拟器并运行 `app`。
2. 选择 `View → Tool Windows → App Inspection`。
3. 选择进程 `com.dayoudu.app`，切换到 `Database Inspector`。
4. 展开 `daily-rhythm.db`，双击表查看数据；需要自动更新时开启 `Live updates`。

可运行这些只读检查：

```sql
PRAGMA user_version;
PRAGMA integrity_check;
SELECT name FROM sqlite_master
WHERE type = 'table' ORDER BY name;
SELECT COUNT(*) FROM plans;
SELECT COUNT(*) FROM ledger_entries;
```

业务表起始为空；进入“我的”后，应用会创建稳定的本机档案。生活记录由用户填写后保存。

## 本次验证结果

- 在模拟器安装并启动 App，Room 自动创建数据库。
- 读取应用停止后的数据库及 WAL 快照，确认版本为 10、业务表共 17 张，Room identity hash 正确。
- 实际表的字段集合、SQLite 类型、可空性、主键顺序，以及 schema 声明的索引列均匹配；`PRAGMA integrity_check` 返回 `ok`，`foreign_key_check` 无结果。
- App 停止并重新启动后，数据库可再次打开，表结构及行数保持一致。
- 三个设备端测试通过：本机档案保存并改名后关闭数据库、重新打开，ID、创建时间和昵称保持；账本事务发生主键冲突后完整回滚，已有档案保留；参数化 SQL 向独立库的 17 张表各写入一行，提交并重新打开后由 SQL 和 Room DAO 读回。
- 测试在随机命名的 `room-verification-*.db` 中运行，测试结束后删除该独立测试库；实际业务库保持空白。
- `:app:assembleDebug`、`:app:lintDebug` 通过，`git diff --check` 通过。本轮没有逐版本重新验证历史迁移，也未执行备份恢复。

## 重新运行数据库测试

使用专门的测试模拟器，并在本目录打开 PowerShell。以下示例设备序列号为 `emulator-5554`，先用 `adb devices` 确认实际序列号：

```powershell
.\gradlew.bat :app:assembleDebug :app:assembleDebugAndroidTest --console=plain
adb -s emulator-5554 install -r app\build\outputs\apk\debug\app-debug.apk
adb -s emulator-5554 install -r app\build\outputs\apk\androidTest\debug\app-debug-androidTest.apk
adb -s emulator-5554 shell am instrument -w -r -e class com.dayoudu.app.data.LocalDatabaseTest com.dayoudu.app.test/androidx.test.runner.AndroidJUnitRunner
```

预期输出为 `OK (3 tests)`。以上安装使用 `-r`，本次验证确认该运行方式保留实际业务数据库。Gradle 的 `connectedDebugAndroidTest` 也可执行这些测试，但其设备清理会卸载目标 App，本次观察到卸载后需重新安装；仅用于无真实数据的测试设备。

完整的模块状态、SQL 连接示例及 17 张表的 118 个字段，见[本地 SQL 存储与模块字段](../deliverables/12-本地SQL存储与模块字段.md)。

2026-10-21 云同步补充：业务 Room schema 仍为 v10 / 17 张业务表；正式应用的 onOpen 另建 5 张独立协议版本的同步辅助表及事务触发器，详见[同步实现](../deliverables/17-三模块云同步实现映射与验收.md)。新增 `CloudSyncTest`，与本文件原有 3 项设备测试合计 10 项通过；云同步往返测试需要按[部署与联调](../deliverables/18-云端部署与手机联调操作.md)连接专用测试后端。JSON 备份不导出辅助队列或登录令牌。

## 保存与备份

日常备份使用 App“我的 → 导出备份”，生成 JSON；当前格式为 v11，可恢复 v8/v9/v10/v11。恢复会替换全部本地记录，操作前先导出现有数据。卸载 App 或清除应用数据会删除设备中的数据库。

运行时可能同时存在 `daily-rhythm.db-wal` 和 `daily-rhythm.db-shm`，这是 SQLite WAL 模式的正常文件。App 运行时不要只复制主 `.db` 文件作为完整备份。

参考：[Android Room](https://developer.android.com/training/data-storage/room)、[Database Inspector](https://developer.android.com/studio/inspect/database)、[AndroidX Test](https://developer.android.com/jetpack/androidx/releases/test)。
