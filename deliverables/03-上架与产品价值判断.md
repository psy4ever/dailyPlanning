# 日有度｜自用与上架判断

日期：2026-10-19。以下商业判断是产品推论，不是市场需求已验证的结论。

## 1. 是否值得做

**值得先做成自己的日用工具，再决定是否商业化。** 你已有明确、反复发生的真实需求，技术上适合逐步完成；但“日程 + 打卡 + 时间统计”本身不足以证明有市场机会。

[TickTick 官方介绍](https://ticktick.com/?language=en_us)已经覆盖任务、日历、专注计时和习惯。因此“功能齐全”很难单独构成差异化。这只是一个代表性竞品比较，尚未完成所有同类 App 的系统调研，也未证明你的设想没有竞品。

自定义价值权重是值得验证的方向：用户可以认为社交、娱乐与收入同样重要，不被固定生产力标准评价。真正难点是让人愿意长期记录和评价，而不是公式本身。

## 2. 建议抓住的亮点

| 方向 | 用户能感知的价值 | 如何验证 |
|---|---|---|
| 自己定义“值得” | 自选维度和权重，理解哪些活动符合当前生活目标 | 用户能解释一条报告为何符合或不符合自己的感受 |
| 计划与实际同屏 | 不只是打卡，还能知道高估了多少、哪里被打断 | 一周后是否主动调整估时与缓冲 |
| 低负担恢复 | 漏记、改期、休息后可以继续，不会连胜清零 | 漏一天后两天内是否回来继续使用 |
| 本地优先与数据自主 | 没有账号也能用，个人生活和工资不必上云 | 飞行模式完整闭环；导出恢复成功 |
| 回报与付出分开 | 娱乐也有价值；同时看时间、金钱、精力，不只有工资 | 用户是否用它改变了一项重复活动的安排 |

首发主张建议是：“用你自己的标准，看清时间花得值不值。” 展示的是个人偏好和自评，不能包装成客观人生评分。

不要首发同时承诺“精准饮食营养师 + 全自动生活教练 + 时间管理平台”。它们需要不同的数据、信任和验证，容易让单人项目失去重点。

## 3. 自用与上架的不同门槛

| 自用可接受 | 对外发布前必须补齐 |
|---|---|
| 只有一个本地 profile | 有账号时的身份与数据隔离；没有账号则如实说明本地模式 |
| 手工维护营养表、记录三餐与加餐，以及睡眠 | 明确“已知热量”与缺失项、营养来源和版本，完善编辑与删除流程 |
| 手机限定一两台验证 | 多系统版本、常见厂商、省电限制、字体放大和无障碍验证 |
| 手动备份 | 升级迁移、恢复路径、用户能理解的数据安全说明 |
| 简单设置页 | 新手引导、权重含义、评分锚点、模型版本与帮助 |
| 免费自用 | 若收费：权益说明、恢复购买、取消/退款说明与渠道政策适配 |
| 本地日志调试 | 脱敏诊断、反馈渠道、支持响应、故障与安全更新能力 |

原生 App 即使离线也可以形成完整产品价值；是否符合特定渠道的当前上架规则，需要按渠道核验。不要把“没有服务器”直接等同于“不能上架”，也不要以为纯离线自动豁免所有要求。

## 4. 上架前的验证实验

### 第一轮：自己连续用两周

记录四项：每天额外操作时间、漏记原因、是否查看复盘、是否根据复盘调整安排。重点判断是在帮助生活，还是制造新的填表任务。

### 第二轮：邀请 10–20 位同类用户体验四周

由你招募，不在本次任务中发送邀请。优先找愿意做计划但经常难以持续记录的人，而非泛泛收集“听起来不错”的反馈。

建议预先写下以下继续投资门槛（内部假设，并非行业基准）：

- 至少 8/10 位完成首次“计划 → 记录 → 查看反馈”的闭环。
- 到第四周，至少 40% 的样本每周有 3 天真实记录或复盘；明确样本和活跃口径，不能只算打开。
- 每日记录操作时间中位数不高于 3 分钟；权重设置后不需要每次重复填写。
- 至少 5 位能说出曾依据报告调整过的具体安排，而非只说 UI 好看。
- 再访谈付费意愿，区分“愿意支付”的表态与实际购买行为；不把小样本解释为市场规模。

若价值评分很少有人补齐，就减少维度数量、把评分集中到晚间或只评价重点活动；配置权重仍保持明确确认，不制造 AI 代填的假数据。

## 5. 收费与成本假设

可探索：基础离线记录免费，进阶分析/模板一次性买断；云同步和持续 AI 服务另设订阅或额度。具体价格需经过用户访谈和渠道成本验证，本稿不虚构最优定价。

单个付费用户的贡献 = 实收 − 渠道/支付费用 − 云与模型变动成本 − 可归属支持成本。月度盈亏平衡用户数 = 固定成本 / 单用户月贡献（贡献为正才有意义）。一次性收入和订阅收入分别建模。

AI 使用成本还包含重试、图片、检索和上下文长度；限制请求频率、缓存周期总结，并让用户在发送前看清上传范围。不要靠出售个人生活数据补贴成本。

## 6. 渠道与资料清单

### 中国大陆 Android 渠道

确定具体商店后，核验开发者主体、软件著作权/名称材料要求、隐私政策、SDK 清单、权限说明、版本签名和 APP 备案适用性。不同商店与业务形态要求不完全相同，不将某一份材料一概说成所有渠道强制要求。

工信部关于 APP 备案的官方解读涵盖互联网信息服务 APP 的备案和分发要求。接入公网服务时，应把备案纳入上线前准备；纯本地工具的具体适用性和渠道资料要求仍须单独确认。[工信部官方解读](https://www.miit.gov.cn/zwgk/zcjd/art/2023/art_39b4f1acc36745b98478e0ec3e07128d.html)

### Google Play（如果选择海外渠道）

按当时 Play Console 要求准备隐私、Data safety、目标 API 和测试资料。饮食规划/营养功能属于需准确申报的健康相关功能范围；不能因为没有接 Health Connect 就省略对应声明。[Google Play 健康功能申报](https://support.google.com/googleplay/android-developer/answer/14738291?hl=en)

本项目定位为生活记录与一般建议，避免诊断、治疗或保证健康效果的宣传。将来涉及特定疾病、饮食治疗或面向未成年人时，需要重新评估功能与适用要求。

## 7. 当前推荐决策

先完成 Android 离线自用闭环；Java/Spring/MySQL 作为可选同步与后续分析服务。用两周验证自己是否愿意持续记录，用四周小样本验证“自定义回报”是否提供了现有工具难替代的价值。通过后再做商店适配、云同步和付费功能；AI/RAG 是否投入由实际问题决定。
