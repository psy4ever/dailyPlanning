# 日有度｜技术架构与算法 v0.2

日期：2026-10-19。本文是工程方案，未部署服务。核心设计：端侧可靠记录、确定性计算、用户自定义回报、AI 提供可审核解释。

## 1. 推荐技术栈

| 层 | 首选 | 原因与边界 |
|---|---|---|
| Android UI | Kotlin + Jetpack Compose | 推荐新 Android 项目方案；与 Java 后端不冲突。若坚持全 Java，可用 Java + XML Views，但不把 Compose 当成 Java UI 框架 |
| 端侧存储 | Room / SQLite | 手机独立落盘，界面读取本地数据库；MySQL 不能替代手机离线数据库 |
| 业务组织 | ViewModel + Repository + Domain services | UI、数据源、计算分开；不要把统计写进页面 |
| 后台任务 | WorkManager | 同步、备份等可延迟任务；不是精确闹钟 |
| 提醒 | Android 通知 + 按场景使用 AlarmManager | 实现时核验当前权限与系统限制；自用先接受普通提醒 |
| 服务端 | Java 21 + Spring Boot 稳定维护分支 | 当前文档支持 Java 21；选依赖兼容的维护版本并锁定，不混用不同大版本生态 |
| 数据库 | MySQL 8.4 LTS | 用户已有方向；使用 UTF8MB4、迁移脚本和备份 |
| 数据访问 | Spring Data JPA + 显式统计 SQL | CRUD 简洁；时间分段/加权计算放领域服务，不靠复杂 SQL 猜含义 |
| 迁移/契约 | Flyway、OpenAPI | 升级可重复、接口可生成客户端；在工程建立时验证 Boot 兼容矩阵 |
| 测试 | JUnit；Android 单元/仪器测试 | 用同一组 JSON 黄金样例约束端侧与 Java 计算一致 |
| AI 扩展 | 后端 AiProvider 接口 + 可选 Spring AI 适配 | 版本匹配后引入；首版 NoOp/RuleProvider，不伪装已接 AI |
| 开发工具 | Android Studio、Android SDK/模拟器、Gradle；服务端可用 IntelliJ IDEA Community + JDK 21 + Maven/Gradle；MySQL Workbench 或 DBeaver | Android Studio 是写和运行 Android 客户端的主工具，Java/Spring 服务端在同一个或另一个 IDE 中开发；工具不等于运行架构 |
| 日常工具 | Git、adb、JUnit、Android Lint、Postman/Insomnia 或 `.http` 请求文件 | 真机安装/日志、版本控制、接口检查；发布前锁定插件与依赖版本 |

不用先上微服务、Redis、消息队列或 Kubernetes。产品边界按完整应用设计，但首版只实现核心模块；将来再按规模决定是否拆成多个 Gradle 模块。Android Studio 可以创建工程、运行模拟器与真机、查看日志和性能；先安装稳定渠道版本与对应 SDK，服务端 JDK/构建工具可在 Android Studio 之外配置。[Android Studio 官方介绍](https://developer.android.com/studio/intro)

官方依据：[Android 离线架构](https://developer.android.com/topic/architecture/data-layer/offline-first)、[Room](https://developer.android.com/training/data-storage/room)、[Compose](https://developer.android.com/develop/ui/compose/documentation)、[Spring Boot 运行要求](https://docs.spring.io/spring-boot/system-requirements.html)、[MySQL LTS](https://dev.mysql.com/doc/refman/8.4/en/mysql-releases.html)。版本在开始编码时按官方维护状态锁定。

### 1.1 模块边界与交付梯度

| 业务模块 | 独有数据与规则 | 对外依赖 | 阶段 |
|---|---|---|---|
| planning 计划 | 计划、修订、重复规则 | 仅引用活动 ID 查执行结果 | 核心 |
| activity 行为时间 | 实际片段、主分类、关联计划 ID | 只通过计划契约校验关联 | 核心 |
| nutrition 饮食营养 | 用户食物表、营养版本、餐次/加餐、摄入项 | 可选向 activity 发布“已记录摄入”事件；不写时间片段 | 核心 |
| sleep 作息 | 入睡/醒来、质量自评 | 可选映射到 activity 的睡眠主类别 | 核心 |
| valuation 价值回报 | 维度、权重版本、活动评价 | 只读 activity 的已确认时长 | 核心 |
| analytics 洞察 | 时间/热量/回报聚合与覆盖率 | 读取各模块公开查询契约；不直接编辑源记录 | 核心 |
| backup 数据管理 | 本地导出、恢复、迁移清单 | 调用各模块导入/导出契约 | 核心 |
| hydration 饮水 | 体积与时间 | 可选关联营养摄入 ID；不改 nutrition 原表 | 后续可选 |
| cycle 生理周期 | 周期事件/症状、私密设置 | 默认不向洞察/AI发布明细 | 后续可选 |
| custom-record 自定义记录 | 模板版本、字段定义、实例值 | 只向洞察暴露用户授权的通用摘要 | 后续可选 |
| sync、ai | 同步队列；建议草稿和引用 | 通过公开契约读取，失败不阻塞核心 | 后续可选 |

Android 依赖方向建议为 `:app → :feature:{planning,activity,nutrition,insights,...} → :core:{model,designsystem,data-api}`，具体文件名是**规划位置，当前仓库没有这些代码**。Spring 先用一个可运行工程，包按上述业务域划分，例如 `com.dayoudu.nutrition`；每个域含 controller/service/repository/domain，跨域通过明确的接口与 ID，不共享可写实体。一个模块能关闭，核心仍能启动和显示；关闭可选模块不删除数据。不要为了“成熟”在没有复用点时建立空壳模块、插件运行时或每个字段一个 Gradle 子项目。[Android 模块化指南](https://developer.android.com/topic/modularization)

自定义记录模板只支持经过定义的简单字段类型（decimal、text、timestamp、choice、boolean），包含 `fieldKey/type/unit/required/privacyLevel`。模板版本与旧记录一起保存；不把它变成任意可执行脚本，也不允许自定义模板直接写核心饮食、计划或周期数据库。插件式页面注册、云端配置与独立发布等能力留待真实规模出现后评估。

### 1.2 你实际需要安装和使用什么

1. **Android Studio**：创建 Android 项目、编写 Kotlin/Compose 页面、用 Gradle 构建、在模拟器或开启调试的 Android 真机运行；其内置 Logcat 用来看崩溃日志，Device Manager 管模拟器。第一次建项目先用单一 `:app` 模块，完成饮食记录与本地存储的最小闭环，再按表中边界提取模块。
2. **JDK 21 + IntelliJ IDEA Community（或熟悉的 Java IDE）**：开发 Java/Spring 服务。服务端单独工程或与 Android 工程并列，不把 Spring 代码编进 APK。用 Maven Wrapper/Gradle Wrapper 锁定构建工具，Spring Initializr 可生成基础工程；具体 Spring Boot 与插件版本以建项时官方兼容表确认。
3. **MySQL 8.4 LTS + 数据库客户端**：运行服务端数据库；DBeaver/MySQL Workbench 只方便查看数据，不参与 App 运行。手机端仍用 Room/SQLite。用 Flyway 保存建表和迁移脚本，不靠手工点客户端维护结构。
4. **Git、adb、API 调试工具**：Git 管版本；adb/Android Studio 在真机安装调试；HTTP 客户端或 IDE `.http` 文件检查将来的 Spring API。第一阶段完全离线开发时不需要先配置公网域名、AI 密钥或服务器。

建议仓库目录在真正开始编码时再创建：`android/`（Android Studio 工程）、`server/`（Spring 工程）、`docs/`（需求和接口）。当前仓库仅有方案文件，以上是规划目录，不代表已安装或已创建。两端共用 `05-接口字段设计.md` 中的领域含义；若开始联调，再把表转换为可校验的 OpenAPI 规范。

## 2. 没有公网时如何运行

```text
Android 界面
   ↓ 读写
Repository → Room（本地事实与修改队列）
   ↓ 可选同步，失败不影响使用
局域网电脑 Spring Boot → MySQL
   ↓ 将来由用户开启
外部模型 API / 本地模型 / 知识检索
```

**A. 纯离线手机**：计划、行为、餐食、睡眠、权重和统计全部在手机完成；不需要电脑常开。Spring/MySQL 可后置，保留 DTO 和同步字段即可。

**B. 没有公网但有局域网**：电脑运行 Spring/MySQL，手机与电脑连同一网络，用电脑局域网地址访问。手机上的 localhost 指手机自身。仅开放所需服务端口给专用网络，并设置设备配对/鉴权；不向手机开放 MySQL 端口。开发 HTTP 仅限 debug 配置；正式版采用经过验证的 TLS/信任方案。

**C. 有公网后**：加入账号、远程同步和 AI 网关，不改变“本地先保存”的核心体验。联网、认证或 AI 故障不应阻塞结束计时。

完全隔离网络的开发机器还需要预先准备 Gradle/Maven 依赖和 SDK；这里的离线运行不等于可以在没有依赖包的情况下离线构建。

## 3. 数据模型

所有可同步实体带 `id(UUID)、owner_id、created_at、updated_at、version、deleted_at、device_id`。单机先用本地 profile；不要收集不必要的身份信息。

| 实体 | 关键字段 / 关系 |
|---|---|
| category | name、kind、color、archived；主类别与价值维度不同 |
| project | name、kind(work/study/personal)、archived |
| plan_item | title、scheduled_start/end、timezone、priority、fixed、status、baseline_version、series_id |
| plan_revision | plan_id、revision、原计划起止、变更原因；支持初始与当前计划比较 |
| activity | category_id、project_id、plan_id(可空)、title、session_status、source |
| activity_segment | activity_id、start_at、end_at、primary_flag；一段仅包含实际运行时间 |
| sleep_log | onset_at、wake_at、awake_seconds(可空)、quality(可空)、linked_activity_id |
| food_definition / food_nutrition_version | food_id、name、brand(可空)、prepared_state(raw/cooked/packaged/unknown)、revision、kcal_per_100g、protein/fat/carbs_g_per_100g(可空)、source_type、source_note、is_user_defined、archived；营养版本不可原地改写 |
| intake_event / intake_item | eaten_at、timezone、meal_type(breakfast/lunch/dinner/snack)、note；food_id、food_revision、consumed_grams(可空)、kcal_per_100g_snapshot(可空)、kcal_total(可空)、data_status；同一餐多项、同日多次加餐 |

| cycle_entry | local_date、event_kind、flow_level(可空)、symptoms(可空)、private_note(可空)；独立权限与备份分类 |
| custom_template / custom_entry | template_id、template_version、field_specs(JSON schema-like)；field_values(按版本校验)、occurred_at、privacy_level |
| attachment | owner_record_id、local_uri、hash、mime、upload_state；照片不要直接塞进 JSON |
| feeling_log | activity_id/date、energy_before/after、effort_1_5、note；均可空 |
| value_dimension | stable_id、user_name、definition、scale_anchors、archived |
| value_model / model_version | name、version、confirmed_at、effective_from；版本不可原地改写 |
| model_dimension | model_version_id、dimension_id、weight(DECIMAL)、scale_definition_snapshot |
| activity_evaluation | activity_id、model_version_id、evaluated_at、revision |
| dimension_rating | evaluation_id、dimension_id、score_0_10(可空)、note、source(user/confirmed_ai) |

| insight_run | window、algorithm_version、model_version、data_revision、coverage、citations、generated_at |

金额用 DECIMAL 和币种，禁止用浮点累加金额。权重保存原值，归一化按需计算；不要只保存四舍五入后的百分比。

时刻保存 UTC instant，另存记录时 IANA timezone（默认 Asia/Shanghai）；日计划的墙上时间和重复规则需保存本地日期与时区。SQL `DATETIME(3)` 本身不带时区，需应用统一按 UTC 编解码。

索引：`(owner_id,start_at)`、`(owner_id,project_id)`、`(owner_id,updated_at)`、`(evaluation_id,dimension_id UNIQUE)`、`operation_id UNIQUE`。重叠约束不是普通唯一索引可以解决的，需事务内检查。

睡眠记录更新相应主活动，避免 sleep_log 与 activity_segment 双算。餐食和饮水是事件；只有用户明确记录“吃饭所用时间”才进入时间构成。自建食物更改营养值时新建版本，已保存摄入项通过快照保持历史统计稳定。

## 4. 核心 API 草案

完整字段、类型、状态、请求/返回样例、页面取数时机见 [接口字段设计](05-接口字段设计.md)，页面元素到接口与规划代码位置的对应见 [原型—接口—代码映射](04-原型接口代码映射.md)。这是**设计契约**，当前无服务端实现。Android 离线版调用本地 Repository；HTTP API 为后续局域网/云同步准备，避免一个 UI 动作先发多次无意义请求。

| 路径 | 意图 |
|---|---|

| `POST /api/v1/activities/{id}/start|pause|resume|finish` | 写会话事件，不靠客户端每秒上传 |
| `POST /api/v1/activities/manual` | 补记；冲突返回冲突区间供用户处理 |
| `POST /api/v1/sleep-logs` | 作息记录 |

| `GET/POST /api/v1/intakes`、`PATCH /api/v1/intakes/{intakeId}` | 三餐/加餐记录；摄入项带食物版本与克数 |
| `GET /api/v1/nutrition/daily?date=&timezone=` | 返回已知 kcal、待补全数与各餐汇总；不能把部分合计命名为全天总摄入 |

| `GET/POST /api/v1/hydration-entries`、`/cycle-entries` | 后续可选模块，权限与存储边界独立 |
| `POST /api/v1/value-models/{id}/versions` | 确认新权重版本；校验非空维度与正权重 |
| `PUT /api/v1/activities/{id}/evaluation` | 按版本保存各维度评价；空值可保留 |
| `GET /api/v1/analytics?from=&to=&timezone=&modelVersion=` | 明确时间窗、模型、数据覆盖率 |

首版无需每个功能都走 API；端侧 Domain 使用同一语义。返回业务字段时带 `schemaVersion`。冲突用 409，校验失败 422；服务端必须按认证身份确定 owner，不信任请求传入的 owner_id。

同步：本地修改与 outbox 在同一事务写入 → 网络可用时推送 operation_id → 服务端版本校验和去重 → 返回 server version → 拉取 server_sequence 后增量。删除使用 tombstone；并发编辑冲突保留双方副本让用户选择，不能只看设备时钟“最后写入获胜”。

## 5. 算法 A：时间构成

输入为主活动的半开区间 `[start,end)`。先裁切到统计窗，再按用户时区本地午夜切片；同类重叠取并集，跨类重叠先提示用户确认主活动。未解决冲突可标记为“待确认”，不能在两个类别都累加。

```text
window = [dayStart, min(nextDayStart, now)]   // 今日只统计已发生
segments = clip(primarySegments, window)
resolved = splitAtBoundariesAndResolve(segments)
duration(category) = sum(resolved durations for category)
unknown = duration(window) - unionDuration(all resolved known segments)
share(category) = duration(category) / duration(window)
recordCoverage = unionDuration(known segments) / duration(window)
```

历史普通日：睡眠 8h、工作 7h、生活 5h、未记录 4h，共 24h，占比 33.3%、29.2%、20.8%、16.7%。Asia/Shanghai 普通日为 24h；支持旅行时按真实日界线算，不能把所有地区所有日子硬编码为 86400 秒。

提供两个明确命名口径：①全天/已发生时间占比，包含未记录；②已记录时间内部占比。不能混用分母。扫线排序复杂度 O(n log n)，个人一天的数据量无需机器学习。

计时恢复：持久化每个起止事件；运行中 UI 使用单调时钟显示。重启后依据持久化时间恢复并提醒核实；检测系统时间显著改变，不静默制造负时长。暂停时间不计入活动。

## 6. 算法 B：计划与实际

- **完成率**：完成项 / 到期且未取消项，同时展示分子分母；取消数单列，避免取消全部就变成 100%。
- **时长偏差**：实际关联片段总时长 − 计划时长；早晚开始偏差单列。部分完成不能仅按耗时判定。
- **时间重合度**：计划区间与实际区间交集 / 计划区间长度；只用于时间执行情况，不等于任务质量。
- 对原始计划和调整后计划分别比较；保留历史基线，不允许事后修改计划使所有偏差消失。
- 没有关联计划的行为也是合法行为；未记录实际时长返回“未记录”，不是 0。

## 7. 算法 C：个人回报的加权模型

### 7.1 活动总分

启用维度 i 的权重为 `w_i > 0`，用户评分 `s_i ∈ [0,10]`：

```text
p_i = w_i / sum(w)
personalReturn = 10 * sum(p_i * s_i)        // 0..100
contribution_i = 10 * p_i * s_i             // 总分可解释分解
```

例：社交 8、娱乐 6、收入 9。

- 社交:娱乐:收入 = 3:3:3 → 76.666… → 展示 76.7。
- 收入:社交:娱乐 = 4:2:2 → (4×9+2×8+2×6)/8×10 = 80.0。

这是用户偏好下的主观指数，假设各维度 0–10 刻度可进行加权。需要明确锚点，不把它解释为科学测量或财务 ROI。避免设置意义重叠的维度（如收入与赚钱能力）而不解释其区别。

### 7.2 缺失与覆盖率

`ratingCoverage = sum(weights of scored dimensions)/sum(all active weights)`。

未评分与 0 必须区分。MVP 只有所有启用维度已评价时显示最终总分；不完整显示“待补充，覆盖率 66.7%”，展示已有分项，不悄悄重新归一化。高级版可以给上下界：未评分按 0 和 10 得到可能范围，必须标“范围”，不能当最终分。

“不适用”也不能每次自动排除而改变分母。用户可以选择另外一个事先确认的场景模型，或明确填写 0 并解释。不同模型得分不可直接混排。

### 7.3 日/周聚合

默认展示各维度的时长加权均分及记录/评价覆盖率：

`dimensionMean_i = Σ(duration_a × rating_ai) / Σ(duration_a with known rating_ai)`。

总分只使用同一模型下评价完整的活动：`periodReturn = Σ(duration_a × personalReturn_a) / Σ(duration_a)`。

同时显示“已评价活动 5/8，已评价时长 6h/记录时长 10h”；没有完整评价时不给总分。时长加权代表“一段已评价时间的平均体验”，不能解释成“今天一共创造多少价值”。不同模型的活动分组展示；重新用当前权重聚合时必须取齐相同维度、标明是重算。

按时长聚合的好处是把一段活动拆成多段不会凭空提高平均分。睡眠是否参与个人回报由用户明确选择分析范围，默认仅分析用户主动评价的活动，并展示范围。

### 7.4 付出与比较

首版采用“个人回报 × 时间”的散点/列表，并附直接支出和精力消耗，不把小时、人民币、疲劳生硬相加。比较范围优先同项目、同类型活动、相同模型和时间窗。

后续用户确实需要“投入产出指数”时，再建立独立投入权重：时间/金钱/精力先按用户设定的基准归一化，并明确公式与截断。不要默认用回报分除以分钟：它会夸大短活动，评分本身也不保证比率尺度。可先用 Pareto 提示“回报更高且时间/支出不更高”，不宣称唯一最优。

## 8. 算法 D：现金回报，作为独立参考

```text
netCash = attributableIncome - directWorkCosts
workRate = netCash / actualWorkHours
occupiedRate = netCash / unionHours(work, commute, requiredUnpaidWork)
```

同期间例：收入扣除直接支出后 ¥8,000，实际工作 160h，通勤 22h；净时薪 ¥50.0/h，含通勤 ¥43.9/h。按到账记录与按劳动归属期记录分开；不能把上月工资到账算作今天劳动收入。必要无偿工作若已含在 work 中，使用并集去重。

缺失收入显示未知；没有工作时长不除零。不同币种不直接相加。学习、休息和社交没有现金收入不等于没有回报。可配置收入目标贡献的评分映射，但必须用户显式确认基准，首版采用自评。

## 9. 算法 E：作息、饮食与安排

**作息**：估计睡眠时长 = 醒来 − 入睡 − 已记录夜间清醒；夜间清醒未知时标“估计”。主睡眠按醒来日展示，时间账本仍按午夜切分。分析入睡规律用相对于参考晚间时点的展开分钟或圆统计，不能直接平均 23:50 与 00:10 得出中午。至少有多日有效记录后再比较趋势，不推断疾病。

**饮食**：首版由用户建立/维护食物营养表，至少填写每 100g 的能量 kcal、来源和生熟/包装状态；蛋白质、脂肪、碳水可选。记录每次食用的可食部克数 `g`，单项 `kcal = kcal_per_100g × g / 100`；每项保留所用营养版本、数值快照及来源。先按高精度 decimal 求和，再在展示层统一四舍五入。单位为 kJ 的包装值可按 `1 kcal = 4.184 kJ` 转换并保留原单位；若包装只给“每份”，先明确每份克数，不自行猜测。配方菜需要分食材和成品份数/出品重量，初期可作为用户创建的单品，标明估算来源。

早餐、午餐、晚餐、加餐是分类，不根据钟点自动改类；同一天可以多条加餐。每日已知 kcal 是所有完整条目之和，不管餐次；缺营养值或克数的条目计入 `incompleteItemCount`，不以零 kcal 代替。展示“已知摄入 N kcal · M 项待补全”，不称“总摄入”，也不自动给通用目标值。饮水若是零能量水可只记毫升；含糖饮料需关联一条营养摄入项，避免漏算或重复算。生熟、额外用油和可食部均需用户确认，照片不能可靠确定隐藏配料和克数。

比手工逐项重填更省事的方案：本地“我常吃的食物”与最近份量、收藏组合餐/配方；以后可从**有授权且适合目标地区**的成分数据库导入候选，由用户核对单位、生熟与品牌后保存。USDA FoodData Central 提供每 100g 营养字段，但其食物与份量未必适合中国餐食，仍需本地化核验。[FoodData Central 字段说明](https://fdc.nal.usda.gov/portal-data/external/dataDictionary) AI/扫码仅负责提出候选，不直接记入确定热量。

**计划建议**：首版用约束与启发式：固定事件锁定 → 保留用户设定睡眠/用餐窗口 → 按优先级/截止时间放入灵活任务 → 检查空档长度 → 插入可配置缓冲。用相似任务历史时长中位数作为建议，样本不足沿用用户估时；可选使用较高分位值留余地。没有可行解时列出冲突与待安排任务，不悄悄压缩睡眠。

缓冲比例初始可建议 20%，但它是可调整的产品参数，不是医学或普遍最优结论。个人回报权重可参与灵活任务排序，不能凌驾于用户锁定事件、截止时间和基本生活安排。

## 10. RAG 与模型 API 的分工

**精确统计走确定性代码，个人事实走结构化查询，解释与建议才交给模型。** RAG 用于“检索可靠知识再生成解释”，不是把所有行为丢进向量库就自动懂生活。

| 能力 | 无网络首版 | 联网/本地模型扩展 |
|---|---|---|
| 时间占比、回报分 | 本地算法 | 仍用同一算法 |
| 日/周总结 | 规则模板 | 模型解释结构化统计，不能更改数值 |
| 食物营养 | 手动条目/离线食品库 | 视觉模型提候选，用户确认后计算 |
| 计划重排 | 约束校验 + 启发式 | 模型提草稿，确定性规则校验再应用 |
| 知识问答 | 已授权离线文档/全文检索 | RAG 增加语义检索与引用 |

推荐路径：用户问题 → 鉴权与数据范围 → SQL/本地聚合 → 按需检索带来源知识 → 构造最少必要上下文 → 模型返回结构化建议 → 数值/时间冲突/来源校验 → 用户确认 → 保存。

RAG 首先收录用户自己的目标定义、已经授权的营养资料和操作说明；文档记录来源、日期、适用范围和版本。小知识库先用全文检索；确实需要语义召回时再增加 embedding 索引，避免为了用 RAG 而上新基础设施。个人记录按 owner 隔离，删除时同时删除派生索引。

模型输出契约示例：`summary、evidence_record_ids、knowledge_citations、proposed_changes、missing_data、uncertainty`。没有来源不写健康结论；检索到的文本视为数据，不能作为系统指令执行。需要明确区分“你的记录显示”“可能的解释”“建议尝试”。

云 API 密钥只在后端，不能打包进 APK。上传前说明实际发送的字段；工资、饮食照片和完整日记默认不作为必需上下文。设置超时、配额、缓存和失败降级。离线本地模型需额外评估设备资源、许可证及效果，首版不依赖它。

### AI 验证目标

建立一套包含正常、缺失、冲突、跨日、过敏信息与恶意知识片段的评测样例：数值与计算结果一致；没有证据不下结论；不能安排到锁定时段；引用可定位；用户拒绝建议后不改数据。识餐评测区分菜品识别与克重估算，不能仅靠菜名识别准确率宣称营养准确。

## 11. 首批必须通过的算法样例

| 用例 | 期望 |
|---|---|
| 23:30–次日 01:00 | 前日 30min，次日 60min |
| 09:00–10:00 与 10:00–11:00 | 相邻不冲突，合计 120min |
| 同类 09:00–10:00 与 09:30–10:30 | 并集 90min，不是 120min |
| 跨类重叠 30min | 要求主活动确认或标待确认，不能双算 |
| 无记录的昨天 | 100% 未记录，不显示娱乐 24h |
| 今天 12:00 查询 | 只以已发生区间统计；未来 12h 单列 |
| 计划已完成、无实际时间 | 完成状态有效；实际时长未知 |
| 权重 3/3/3，评分 8/6/9 | 76.7/100 |
| 收入/社交/娱乐 4/2/2，评分 9/8/6 | 80.0/100 |
| 权重全部为零或无维度 | 拒绝确认，定位到字段 |
| 一维未评分 | 不输出最终总分，显示权重覆盖率 |
| 同评分活动拆成两段 | 时长加权均分不变 |
| 权重更新 | 旧报告仍能恢复旧版本结果 |
| 无收入/无工作小时 | 返回缺数据，不生成 Infinity/0 时薪 |
| 重复推送同 operation_id | 只保存一次 |
| 导出后清空测试库再恢复 | 条数、关系、权重版本、照片引用一致 |

## 12. 安全、性能与可维护性

本地使用 Android 应用沙箱；收入等敏感信息支持应用锁。明确系统云备份策略，不能一边声称仅本地一边默认把敏感数据库备份到第三方。导出的明文文件先提示包含哪些数据；加密备份需考虑密码丢失与恢复方案。

上云后补齐身份认证、数据隔离、TLS、服务器备份及恢复演练、删除级联、脱敏日志和最小权限。统计缓存标记数据/算法/权重版本，记录更改使缓存失效。性能目标：常见页面在普通测试手机上可交互时间约 1 秒以内、保存交互反馈约 200ms 内；这是待测目标，不是当前结果。

提醒方案参考 [Android AlarmManager](https://developer.android.com/develop/background-work/services/alarms)。须在目标真机测试省电、通知权限、重启和后台限制，不承诺操作系统强制停止后仍可提醒。
