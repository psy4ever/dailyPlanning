## 推荐架构与成本

推荐腾讯云轻量应用服务器（Lighthouse），Ubuntu 24.04 LTS x86_64，单机运行反向代理、Java 21 / Spring Boot 后端和 MySQL 8.4 LTS，以 Docker Compose 描述部署。Spring Boot 的具体维护版本、容器镜像补丁版本及 digest 在编码和部署验证时固定；Android 构建继续使用 JDK 17。

```text
Android 页面 → Room 本地保存 + 同事务同步队列
                         ↓ HTTPS，认证后重试同步
轻量云服务器：反向代理 → Spring Boot API → MySQL 持久卷
                                             ↓ 定时备份
                                  独立位置的加密备份副本
```

这是个人起步单机方案。MySQL 与后端同机，后续仍需维护、备份及恢复演练；独立备份副本不只放在该服务器同一块磁盘。托管云数据库可在后续按运维需求迁移。

## 按顺序执行

### 第 1 步：注册与选型，不产生部署变更

1. 在[腾讯云](https://cloud.tencent.com/)注册本人账号，并本人完成实名认证。
2. 打开[轻量服务器产品页](https://cloud.tencent.com/product/lighthouse)和[官方活动页](https://cloud.tencent.com/act/pro/lhsale)，查看符合上述内存、系统和地域要求的套餐。
3. 记录 CPU、内存、系统盘、带宽、月流量、地域、系统镜像、购买时长、总价、续费价、自动续费状态。先不提交付款。
4. 账号密码、短信验证码、身份证材料、访问密钥和数据库密码不写入项目或聊天。注册及实名认证由本人在官方页面完成。

验收：本人能进入控制台，得到一份具体候选配置和费用。后续部署只需要按阶段提供实例地址和经过配置的访问方式，不要求共享主账号密码。

### 第 2 步：在本地完成可部署的后端闭环

计划新增 `server/` 并扩展已有 `deploy/`，实现自用账户和计划、记账、饮食三个模块接口。服务器和 MySQL 已提前配置完成；后端代码、迁移、部署文件齐备且本地验收后，再部署到已有服务器。

需要交付：

- 固定版本的构建 Wrapper、Java 21 配置、Spring Boot 工程与自动化检查。
- MySQL 迁移文件和最小权限应用账户；MySQL 端口不发布到公网。
- 独立账户表和用户归属；当前 Android `local_users` 只是本机档案，绑定云端账号时需明确关联，不能直接当作认证身份。
- 认证及三个模块的新增 / 查询 / 更新 / 删除与状态操作接口，并锁定契约。范围包含计划改期、活动计时、食物历史版本及摄入营养快照。服务端从认证上下文确定拥有者，不信任请求中的 ownerId。
- 金额、时间、空值、删除、版本冲突及重复请求的测试。
- Dockerfile、Compose、本地配置模板；真实密码和令牌不提交 Git。

验收：从干净的数据库执行迁移，登录后可保存并查询计划、账目和饮食各模块的关联测试数据；未登录请求被拒绝；重启容器后记录及关联保留。健康检查的成功与数据库可用分别验证。

### 第 3 步：确认订单并创建服务器

在第 2 步通过后，使用第 1 步记录的配置核对实际订单。活动价若更适合且满足要求，可选择活动套餐；付款前核对续费和自动续费。先购买一个实例。

验收：实例运行，系统和架构符合方案，能够通过专门配置的 SSH 访问方式登录；记录实例 ID、地域和到期日。更改/重装操作系统之前先确认实例内是否已有数据。

### 第 4 步：服务器基础环境

安装官方来源 Docker Engine 和 Compose，固定并记录版本；建立部署用户、目录和仅服务器持有的环境配置。验证目标地域能获取所需镜像；必要时通过可访问的镜像仓库存储已验证镜像，并记录 digest，避免依赖未知公共加速地址。

端口规则：SSH 仅向管理来源开放；公网业务使用 HTTPS；MySQL 3306 和后端内部端口不直接对公网发布。Docker 端口发布与主机防火墙一并检查。

验收：`docker version`、`docker compose version` 可用；重启策略、持久卷和最小权限已配置；从公网不能直接连接 MySQL。

### 第 5 步：域名、HTTPS 与正式服务准备

按最终访问方案配置域名和证书续期。使用中国内地云资源提供公网网站或 APP 服务时，在上线前按实际服务场景完成必要备案，遵循[腾讯云使用限制](https://cloud.tencent.com/document/product/1207/44376)与[备案指引](https://cloud.tencent.com/document/product/243/45097)，不将“个人自用”当作自动免除相关要求的结论。

开发联调阶段采用受限访问；正式手机同步使用经过正常验证的 HTTPS，不在 App 里跳过证书校验。具体证书和域名配置到本步骤时核对。

验收：正确主机名可建立 HTTPS，证书有效，续期方法及入口开放范围有记录。

### 第 6 步：部署后端与 MySQL

使用已经本地验收的同一 Compose、镜像版本和迁移流程部署到云端。真实环境配置单独创建。数据库 schema 由迁移文件建立，不直接把 SQLite 建表语句复制给 MySQL。

验收：健康检查和数据库检查成功；认证后 API 能创建和查询三个模块的关联测试数据；服务重启后数据保留；权限隔离和无认证访问检查通过。

### 第 7 步：Android 接入计划、记账、饮食同步

保留 Room 本地保存，增加网络权限、认证客户端、同步状态和重试队列。冻结与当前三个模块实体及操作匹配的 API；共同同步层覆盖各模块全部写入入口及其关联数据，字段以[三模块范围](16-三模块云端接入范围与验收.md)和实际本地实现为准。

核心要求：

- 本地修改与同步任务在同一 Room 事务提交，网络失败仍可保存记录。
- `operationId` 保证重试幂等；服务端版本和本地编辑版本分开记录，不直接把本地递增的 version 当作已确认的服务端版本。
- 冲突返回明确结果，首版要求用户选择，不悄悄覆盖另一设备的更新。
- 删除保留可同步标记；增量拉取使用服务端变更序号，不只依赖手机时钟。
- 旧本地数据首次绑定账号时有明确确认和导入过程，能够回退到已导出的本地备份。

验收：离线新增计划、账目、食物及摄入 → 联网上传 → 云端可查 → 另一干净测试安装登录后拉取成功。三个模块均检查重复上传不重复创建、冲突有提示、删除不会被旧数据复活；计划历史与计时、饮食版本与营养快照保持完整。

### 第 8 步：备份、恢复与长期运行

数据库按计划生成一致性备份，写到独立存储位置，设置访问权限、加密和保留周期；检查备份失败、磁盘不足和实例到期提醒。先以每天备份一次、保留最近 7 天为起步目标，具体保留策略随数据量调整。

验收：将备份恢复到隔离的新数据库实例/容器，核对行数和关联，实际接口可读。只有备份文件存在不算恢复验证成功。同机数据库卷提供持久化，不替代独立备份。

### 第 9 步：三个模块联合验收

按[三模块完成标准](16-三模块云端接入范围与验收.md)逐项验收计划、记账、饮食及关联数据，确认共同账号下的数据恢复和离线重试。三个模块均通过后标记本轮云端接入完成。保留现有本地睡眠记录及其活动重叠校验；暂停的回报/洞察入口继续按原状态保留。
